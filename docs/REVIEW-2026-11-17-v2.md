**Reviewer stance:** experienced, has shipped production code in Slim, Express, FastAPI, Symfony API, and hand-rolled micro-frameworks. Not here to be kind; here to tell you where the framework stands *from the seat of the developer who builds the app in `modules/`*.

**Scope:** full re-read of the tree (src/, modules/, bin/, public/, tests/), docs (RULES, ARCHITECTURE, PRD, REPORT, CHANGELOG), and the boot chain verified empirically end-to-end.

## 0. Corrections to the prior review (read this first)

The earlier draft owed you **one clear correction** and **one nuance**. Everything else in the findings below survives verification. I re-read the whole tree file-by-file and re-ran the boot chain before rewriting.

**The `.config` error — corrected, with the actual truth.**
In the prior review I claimed `.config` "does not exist; request dies silently; `basepath` = `public/` but `.config` targets `dirname(basepath)/config`." That was wrong in three ways. The verified truth:

1. `public/index.php` sets `basepath = realpath(__DIR__)` = **`public/`** (not the project root).
2. `index.php` then does `@require $call('implode','.',[ $call('dirname', basepath).sep, 'config' ])`. `dirname('…/public') . sep . 'config'` = **`…/app/.config`** — a **dot-named** file at the project root (the dot is part of the filename). That file **does** exist and is tracked.
3. `.config` then does `@include_once $call('implode','.',[ $call('dirname',basepath).sep,'supports' ])` = `…/app/.supports` — also a dot-named file at root, also exists and is tracked.
4. On Windows (and any case-insensitive FS), `…/app/.config` and a hypothetical `…/app/config` are distinct; what actually resolves is the literal dot-named file.

So the boot chain is: `public/index.php` → `@require …/app/.config` → `@include …/app/.supports` → `Boot::registerAutoloader()` → `read_directories()` tokenizes the *source text* of `public/index.php` at runtime to pull out the `$directories` map, then `define('system',…)` / `define('modules',…)` / `define('nskernel',…)` as runtime constants. I verified end-to-end that `GET /` → landing HTML and `GET /health` → JSON `{status:ok}` through this chain. **It works. The problem is opacity, not brokenness** — the four-file hidden-dot chain plus a source-tokenizer is something a module developer should *never* have to think about, and (as it stands) the constant-definition side effect leaks into `Response::view()`.

**The `is_callable` out-param error — corrected.**
The sub-reviewer claimed `is_callable('call_user_func', false, $call)` leaves `$call` unset (fatal). **FALSE.** PHP semantics: for a plain function, the by-ref third argument **receives the function name on success**. Verified empirically: `is_callable('call_user_func', false, $fn)` → `$fn === 'call_user_func'`. So `$call('realpath', __DIR__)` is `realpath(__DIR__)`. No fatal. The chain works.

**What survives in the draft.** The `Route::compileRegex()` escape gap is real (the comment at `Route.php:112` says "Escape anything left that PCRE would treat as a metacharacter" and **no code does it** — verified against the current source). `Model::find()` discarding the queued `where` is real. `Pipeline` mutating the shared instance per request is real (`Kernel.php:117-125`). `Config` never being wired into `Boot` is real. `Database::fromEnv()` `root/root/local/10028` fallbacks are real. The `RateLimiter` DoS claim in the draft was *also* wrong (the limiter does **not** read `X-Forwarded-For` — it keys on REMOTE_ADDR), but the forward-looking trust-proxy risk is still valid and is re-stated below as M5. None of these need re-proving; they're re-stated below in the new POV.

# BoneRADF World-Class Review — POV: the module developer

**The question this review answers** is not "is the framework's internals elegant?" It is: *"I'm a developer who is going to build an application by writing code inside `modules/<Name>/` and not touching `src/`. How fast can I ship, where will I get confused, and is this framework a realistic choice for my team?"* That POV inverts the prior review: the boot chain (`.config`/`.supports`/`read_directories`) is now a **non-issue for the module developer** — they never read it, it's encapsulated behind `public/index.php` and `bin/bone`. What *does* matter is everything inside the module boundary: the module contract, the `Controllers/`/`Models/`/`Services/` layers, `Config/{modules,routing}.php`, the `Database::fromEnv()` wiring, and the test story.

## 1. Ease of Use — from inside a module

**The module boundary is the framework's best design decision, and it's where this POV lands.**

What's excellent:
- **Adding a module is a closed, self-contained task.** Create `modules/MyThing/` with `Config/modules.php` + `Config/routing.php` + `MyThingModule.php` (+ `Controllers/`/`Models/`/`Services/` as you need). Zero edits to `src/`, zero edits to `bin/`, zero edits to `public/`. That's better than Mezzio's plugin manager, better than Express's scattered `app.use()`, and on par with Laravel service providers. The "routing.php is the activation switch" trick (empty = inert) is the cleanest I've seen.
- **Each module layer has a sharp contract.** `Controllers/` = HTTP only. `Models/` = the *only* SQL. `Services/` = zero SQL. That's a real architectural boundary, not a folder suggestion. A new dev can learn "where does my logic go?" in one paragraph.
- **`Database::fromEnv()` kills the duplicate-connection problem** — a module's `boot()` wires `new UserModel(Database::fromEnv())` and never touches `BONERADF_DB_*` env vars itself. That's the right separation: DB settings are system-level, module code is clean.

What hurts (in order of pain, module-developer POV):

1. **There is no `bone make:module`.** Today "add a module" = open `modules/Auth/` and copy-paste five files, then fix the five namespaces (`Modules\Auth\…` → `Modules\MyThing\…`). `modules/Test` in the tree is the literal proof: it has the `Testervice` typo, a leftover `use` for a service that doesn't exist yet, and a commented-out `boot()` line. That's what "copy the sample and pray about namespaces" looks like. This is the #1 DX gap from the module-developer POV — **more important than the boot-chain opacity, because the module developer hits it every single time they add a module.**
2. **The module's `boot()` has a foot-gun: `Database::fromEnv()` throws on first call, and there's no graceful path.** If a module needs the DB but `BONERADF_DB_*` is unset, `boot()` fatals with `PDOException` on the first request that touches a model. There's no "this module needs the DB but it's not configured → inert with a clear message" path. The activation switch is `routing.php`, not DB-availability, so a module with routes but no DB config boots, shows `active` in `bone modules`, then 500s on every request that touches a model. For a module developer shipping a fresh install, that's a confusing failure mode: "I added my module, it shows active, then everything is a 500."
3. **The `Model` base class is good but its `find()` semantics will bite.** `Model::find($id)` builds a *fresh* QueryBuilder and silently discards any chained `where()` you queued. `MyModel::where('status','active')->find(42)` returns the row with `id=42` **regardless of status** — the `where` is dropped. The docblock says "discards any pending chain" but no module developer reads the base-class docblock before their first `find()`. This is a real trap.
4. **The seed files duplicate credentials in three places** (`modules/Auth/seed.php`, `modules/Resources/seed.php`, `tests/p6.php`). A module developer adding a third module's seed now has a fourth copy. `Database::fromEnv()` makes centralization trivial; nobody has done it yet.
5. **No `.env` loader, no `bone init`.** A module developer doing a fresh install has to know to set `BONERADF_DB_DSN` / `BONERADF_DB_USER` / `BONERADF_DB_PASS` by hand (or hit the `root/root/local/10028` fallback). No scaffolding command writes a `.env` with the right keys. Compare `laravel new` (writes `.env`), `rails new` (writes `database.yml`), FastAPI (Pydantic `Settings` reads `.env` by convention). This framework has none of that.

**Verdict on ease of use (module POV):** the *module* DX — the closed boundary, the layer contract, the activation switch — is genuinely better than Slim/Express and on par with Laravel service providers. The *install* DX (no generator, no `.env` scaffold, no DB-availability-aware module activation) is the gap. A module developer who already has the framework booting can ship fast; a module developer doing a fresh install has to do several things by hand that other frameworks automate.

## 2. Logic Clarity — the model-layer surface a module developer actually uses

A module developer touches exactly this API surface, and I traced it end-to-end:

```
MyModule::boot()
  └─ new MyModel(Database::fromEnv())          // Model constructor: (PDO $pdo, ?string $table=null)
  └─ $container->instance(MyController::class, new MyController($myService))
MyController->show(Request $req, array $params)
  └─ MyService::find(int $id)
      └─ MyModel::find($id)                    // fresh QueryBuilder, discards queued where
          └─ QueryBuilder->table('my_table')->where('id','=',$id)->get()  // prepared
MyService::listAll()
  └─ MyModel::listAll()
      └─ QueryBuilder->select('id','name','created_at')->orderBy('id','ASC')->get()
```

Clarity problems, in order of how much they cost a module developer:

- **`Model`'s table is explicit, not inferred — a strength.** `Model` throws `RuntimeException: <Class>: $table is not set` at construction if the subclass doesn't set `protected string $table`. `UserModel` sets `'users'`, `ResourceModel` sets `'resources'`. There's **no** silent singular-inference foot-gun; a module developer *must* declare the table or the model won't construct. That's the right call — it removes the #1 "why is my model returning empty?" bug that plagues frameworks with naive table inference (Eloquent's `Post` → `posts` assumption). The cost is one line per model (`protected string $table = 'users';`), which is trivial.
- **`Model::find()` + `where()` chain reset** (re-stated from §1.3). A module developer will write `where('x','=',1)->find($id)` and be surprised the `where` was dropped. Highest-frequency model-layer foot-gun.
- **The `Services/` zero-SQL rule is a convention, not an enforcement.** Nothing stops a module developer from writing raw `QueryBuilder` calls inside a `Service`. The "SQL lives exclusively in `Models/`" claim (ARCHITECTURE §5) is doc-only. A code review will catch it; a runtime won't. For a "world-class" framework, acceptable for v1 but worth noting: the boundary is social, not structural.
- **The three house path helpers (`interlace`, `pathify`, `namespacify`) are invisible to the module developer** — they live in `.supports` and module code never calls them. Good. But `namespacify` is used *inside* `Boot::moduleConfig()` on the manifest's `'class'` string, which means a module developer who typos their manifest class name gets a "class not found" error at a location that doesn't match their typo (because `namespacify` silently re-derives PascalCase). The error message carries the clue but it's easy to miss.
- **The `Model::with()` eager loading is well-designed** — one bulk `IN()` per relation, N+1-guarded, unknown relation → `RuntimeException` with the offending name. The p7 counting-PDO test proves the "1 extra query per relation" contract. Good. The only gap: chaining `with('a','b')` on one instance and `with('c')` on a different instance works (reset per instance) but is undocumented at the call site.

**Verdict on clarity (module POV):** the request-flow logic is clean and short (30-line `Pipeline`, 60-line `Model`, 40-line `Router`). The model-layer surface is where a module developer spends 80% of their time, and that surface has **one real foot-gun** (`find()` dropping the queue) that will cause "why is this empty?" debug sessions. The table-explicitness is a *strength* (no silent inference). Neither is hard to fix; the `find()` one is undocumented at the call site.

## 3. Viability as a Headless Framework Choice — for the team that builds in `modules/`

Concrete, honest comparison (module-developer lens):

| Dimension | BoneRADF | Slim 4/5 | Laravel (API-only) | Symfony API | Express | FastAPI |
|---|---|---|---|---|---|---|
| Adding a feature module | copy-paste 5 files, fix 5 namespaces | add a controller + route line | `php make:controller` + route | add a controller + route | add a file + `router.get` | add a file + `@router.get` |
| Module isolation (no global leak) | **strong** (explicit DI, no registry) | good | good (providers can leak) | good | weak (globals common) | good (FastAPI deps) |
| SQL-injection-free data access | **unique** (prepared-only, no raw) | n/a | Eloquent `whereRaw` escapes | Doctrine raw | n/a | n/a |
| Security defaults ON | **unique** | no | partial | no | no | no |
| Where you spend your dev time | **inside `modules/<Name>/` — the whole app is there** | config + controllers | app/ | src/ | routes + controllers | routers |
| Ecosystem you can lean on | **none** | strong | dominant | strong | dominant | strong |

**What this means for the team building in `modules/`:**

- **Your entire application is the `modules/` folder.** `src/` is the framework and you never touch it. `public/`, `bin/`, `.config`, `.supports` are boot plumbing and you never touch them. That's a *very* clean separation: the framework is the shell, the modules are the app. This is closer to a "microservice kit" than to Laravel's "framework + app in the same tree." For a team that wants "we only ever write in `modules/`," this is a strong fit.
- **The trade-off is the reverse of Laravel.** Laravel gives you a huge ecosystem (queues, events, broadcasting, Sanctum, etc.) and a `make:` generator for everything. This gives you *none of that* — no queue, no events, no broadcasting (locked out by D8), no generator (deferred to v1.1). You get a smaller, sharper core and you build the rest by hand. If your app is "auth + a few CRUD resources + a landing page," this is perfect. If your app needs background jobs, websockets, or a rich admin, you'll be hand-rolling or reaching outside the framework.
- **The "security ON by default" is the real differentiator** for a team that doesn't want to remember to wire CSRF, rate-limiting, and security headers on every route. Express/Slim/Laravel all make you wire them; this ships them on. For a small team shipping a public API, that's a genuine safety win.
- **The honest viability call:** as a *framework you write your app in* (module POV), BoneRADF is a **credible, defensible choice for the "small, secure, single-purpose API" niche** — think: an internal tool, a SaaS's public API, a mobile backend with auth + CRUD. It is **not** a credible choice for "the next big thing" that needs a queue, websockets, or a rich package ecosystem, because those are locked out by design. The question the team should ask: *"do we need the ecosystem, or do we need a small secure core we can fully control?"* If the latter, this is a strong pick. If the former, use Laravel/Symfony.

**Bottom line on viability (module POV):** it is a strong v0.9 *for its niche* and the `modules/` boundary is the framework's best design decision. The two blockers to "choose it for a production team" are: (a) no generator (every module is copy-paste today), and (b) no install scaffolding (no `.env` writer, no `bone init`). Both are v1.1 work and both are high-ROI.

## 4. Findings (Critical / Major / Minor / Strengths)

### CRITICAL (from the module-developer POV)

- **C1. No `bone make:module` — every new module is copy-paste of `modules/Auth/`.** This is the #1 adoption blocker from the module POV. `modules/Test` (shipped in the tree) is the literal example of the failure mode: `Testervice` typo, a `use` for a non-existent service, a commented-out `boot()` line, and a namespace that had to be manually fixed. FastAPI/Slim/Laravel all ship a generator; this defers it to v1.1. *Fix: ship a generator now — it's the single highest-ROI DX feature for the module developer.*

- **C2. `Database::fromEnv()` fails closed with no module-level graceful path.** A module whose `routing.php` is non-empty (active) but whose DB is not configured will boot, show `active` in `bone modules`, and 500 on every request that touches a model. There's no "module needs DB but DB is unset → inert with a clear message" path. For a module developer doing a fresh install, that's a confusing failure. *Fix: either fail boot with "module 'X' is active but BONERADF_DB_DSN is unset" or let the module's `boot()` catch the DB failure and self-deactivate.*

### MAJOR (module-developer foot-guns)

- **M1. `Model::find()` discards the queued `where()`.** `where('status','active')->find(42)` returns the `id=42` row regardless of status. The docblock documents it; no call site enforces it. High-frequency foot-gun. *Fix: make `find()` an alias for `where('id','=',$id)->first()` that *respects* the queue, or rename the method to `findOnly($id)` to make the discard explicit.*

- **M2. `Pipeline` mutates the shared pipeline per request** (`Kernel.php:117-125`). Route-specific middleware is re-registered on every request rather than compiled at boot. At this scale it's cheap, but it violates ARCHITECTURE §3 step 6 ("route table read-only during dispatch") and will misbehave if anyone holds a `Kernel` across requests (the FPM reuse case). *Fix: compile route middleware into the route at boot, not at dispatch.*

- **M3. `Config` is never wired into `Boot::init()`** — the typed-config layer (ARCHITECTURE §9) is dead on the runtime path; secrets come straight from `getenv()` at the call site. The "env > file > defaults" precedence is aspirational. Either wire it (load `BONERADF_*` into a typed `Config`, bind into the container, have `Database`/`AuthGuard`/`CsrfGuard` read from it) or delete `src/Config/` and document env vars as the only config. *Fix: wire it, or delete it. Don't ship it half.*

- **M4. `RateLimiter` — safe today, dangerous by default tomorrow.** Currently it keys on `$req->ip()` (REMOTE_ADDR), so the unbounded-`X-Forwarded-For` DoS is *not* in the code. But the moment a dev "helpfully" adds `X-Forwarded-For` support (which every API behind a load balancer needs), they reintroduce the unbounded-bucket DoS. *Fix: add a `trustedProxies` config key now (even if unused) + a comment, so the next dev does it right.*

### MINOR

- **m1. `Route::compileRegex()` — the metachar-escape step is missing.** The comment at `Route.php:112` says "Escape anything left that PCRE would treat as a metacharacter" and no code does it. A literal `.` in a pattern matches any char: `GET /api/a.b` matches `/api/aXb`. Low probability today (no shipped route uses a dot), real bug on the next dotted route. *Fix: `preg_quote` the literal segments before wrapping in `~^…$~`.*
- **m2. `QueryBuilder::count()` clobbers `$this->select` permanently** (`count()` sets select to `COUNT(*)`); `first()` sets `$this->limit=1` permanently. Chain reuse is broken for raw `QueryBuilder` users (the `Model` layer resets it, so module developers using the `Model` are safe; anyone using `QueryBuilder` directly is not). *Fix: clone the builder for terminal calls, or restore state after.*
- **m3. `FileLogger::redact` only redacts one level deep** — `context: ['user' => ['password' => …]]` is *not* redacted. A module developer logging a nested user object leaks the password. *Fix: recursive redact.*
- **m4. `tests/p8.php` uses `exec()`** — violates RULES.md's "no `exec()`" rule (the rule is unconditional, tests included). Replace with a direct manifest check.
- **m5. `modules/Test/` ships WIP cruft** — `Testervice` typo, unused `use`, commented-out `boot()` line. Either finish it or delete it; don't ship it as the "new module" example.
- **m6. `seed.php` files duplicate DSN/credentials in three places** — centralize.
- **m7. `Validator` `in` rule casts the value to string** — `in:admin,2` won't match int `2`. Coerce both sides.
- **m8. `Boot::handler()` calls `$controller->{$method}()` with no existence check** — a typo in `routing.php` (`['AuthController::class','logn']`) → generic 500, not "method logn not found." *Fix: `method_exists` check with a clear message.*
- **m9. `public/index.php`'s catch block `die()`s with HTML** — a "headless JSON framework" returns an HTML page on boot failure. The envelope contract is broken at the moment it's most needed. *Fix: `Response::error('BOOT_FAILED', …, 500)->emit()` even in the catch.*
- **m10. `RbacGuard` is unreachable at runtime** — no module registers it, and the route-middleware-by-name path can't produce one (it needs a per-permission constructor). The "RBAC ON by default" claim in CLAUDE.md D5 is not true of the code. Either wire it into the default pipeline for protected routes, or soften the D5 claim to "RBAC available, opt-in per route."

### PRONOUNCED STRENGTHS (module-developer POV)

- **The `modules/` boundary is the framework's best design decision.** The entire application is `modules/`; `src/` is the shell you never touch. That's a cleaner separation than Laravel (where `app/` and `vendor/` are entangled) and closer to a "microservice kit." For a team that wants "we only write in `modules/`," this is a strong fit.
- **The layer contract (`Controllers/` HTTP-only, `Models/` the only SQL, `Services/` zero SQL) is real and enforceable by review.** A new dev can learn "where does my logic go?" in one paragraph. That's rare in hand-rolled frameworks.
- **`Database::fromEnv()` is the right call** — DB settings are system-level, module `boot()` is clean. The duplicate-connection problem (each module opening its own PDO) is solved with one shared memoized PDO.
- **The AR `Model` + `Relation` layer with the N+1-guard test** (`tests/p7.php` counting-PDO) is better-shaped than Eloquent's public eager-load API. The "1 extra query per relation" contract is *proven*, not assumed.
- **`ponytail:` comments are the best self-documentation in any framework I've reviewed** — every deliberate limitation names its ceiling and upgrade path. A module developer reading `Model.php` sees exactly what's deferred and why. This scales.
- **The micro test runner (207/207, 60-line runner)** is PHPUnit-shaped enough to drop into CI. A module developer writing module tests gets a zero-dependency runner that exits non-zero on failure — no `composer require` needed.
- **Security defaults ON** (CSRF + rate-limit + 5 headers + fail-closed RBAC-when-wired) — no mainstream framework ships a headless API with every route covered out of the box. For a small team shipping a public API, that's a genuine safety win that saves a week of "remember to wire CSRF on every route" work.

## 5. Top 5 Recommendations (module-developer POV, ranked by ROI)

1. **Ship `bone make:module` now (don't wait for v1.1).** Generate the full `modules/MyThing/` skeleton (manifest, routing, controller, service, model, module class) from a name, with namespaces pre-filled. Add a `bone make:module --with-db` flag that also generates a `seed.php` with a `Database::fromEnv()` call. *Why:* this is C1 and it's the #1 module-developer blocker — every single new module is copy-paste today, and `modules/Test` is the proof of the failure mode. Anchor: `laravel make:controller`, `rails generate` — every serious framework ships this in v1.

2. **Fix `Model::find()` semantics** (M1). Make `find()` respect the queued `where()` (or rename to `findOnly($id)` to make the discard explicit). *Why:* this is the highest-frequency "why is my model returning empty?" bug a module developer will hit. A 15-minute fix that removes the most likely first-week debug session. Note: the explicit `$table` requirement (no silent inference) is already correct and should stay — that's a strength, not a bug.

3. **Add a DB-availability-aware module activation path** (C2). When a module's `routing.php` is non-empty but `Database::fromEnv()` can't connect, fail *boot* with "module 'X' is active but the database is not configured" instead of booting and 500ing on the first request. *Why:* the module developer's fresh-install path is "add my module, it shows active, then everything is a 500" — that's a confusing failure. Make it a clear, actionable boot error.

4. **Wire `Config` into `Boot::init()` or delete it** (M3). Load `BONERADF_*` env into a typed `Config`, bind it into the container, and have `Database`/`AuthGuard`/`CsrfGuard` read from it (killing the `root/root/local/10028` fallbacks). Or delete `src/Config/` and document env vars as the only config. *Why:* the module developer reading `Database.php` sees hardcoded LocalWP credentials and concludes the "secrets from env" decision (D9) is unenforced. Either make it true or stop promising it.

5. **Fix the `Route::compileRegex()` escape gap + compile pipeline middleware at boot** (m1 + M2). `preg_quote` the literal pattern segments; move route-middleware resolution from `Kernel::dispatch` to `Boot` so the pipeline is read-only during dispatch. *Why:* the first is a real (low-probability) routing-correctness bug on the next dotted route; the second restores ARCHITECTURE §3 step 6 and makes the FPM-reuse case safe. Both are small, both are "the framework is correct, the docs say so, but the code doesn't do it" gaps.

---

**Bottom line (module-developer POV).**

The `modules/` boundary is this framework's strongest design decision — the entire application is a folder you own, `src/` is a shell you never touch, and the layer contract (`Controllers/` HTTP-only, `Models/` the only SQL, `Services/` zero SQL) is real and enforceable. The AR `Model` + N+1-guard is better-shaped than Eloquent's public API, and the `ponytail:` convention is something other projects should copy.

But from the module-developer POV, the two blockers are both *DX gaps, not correctness bugs*: (1) no generator — every module is copy-paste today, and (2) no install scaffolding — no `.env` writer, no `bone init`, no DB-availability-aware activation. Fix those two and the framework becomes a genuinely credible choice for the "small, secure, single-purpose API" niche. As it stands, it's a strong v0.9 for a team that *already knows the conventions* and is willing to copy-paste; it's not yet the framework a team would *choose over* Slim for a new build. The model layer's explicit-`$table` requirement (no silent inference) and the N+1-guarded eager loading are genuine strengths that should be preserved and highlighted in any marketing of the framework.

The marketable claim, module-developer POV: **"Your entire app is `modules/`. The framework is the shell, never the app. Security is ON by default. SQL injection is structurally impossible. And you never touch `src/`."** That's a real, defensible position. The five recommendations above are what turns it from "a framework I can build in" to "a framework I'd pick."
